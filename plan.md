## Фаза 10 — Явні дії, контекстні списки та повторювані розклади v2.5.0 (Завершено)

### Рішення щодо голосових повідомлень

1. Голосове повідомлення завжди проходить лише шлях `завантаження -> транскрибація -> форматування -> показ тексту`. На цьому шляху інструменти та будь-які зміни БД мають бути технічно вимкнені, а не лише заборонені промптом.
2. Дія з транскрипції запускається тільки явною кнопкою «Обробити як інструкцію». Якщо відкритий сценарій очікує уточнення, окрема кнопка дозволяє використати транскрипцію як відповідь на це уточнення.
3. Кнопка має бути прив'язана до конкретної транскрипції через ID її персистентного запису. Поточний пошук «останньої транскрипції в чаті» не використовувати, бо паралельні голосові можуть підмінити одне одного.
4. Текстові повідомлення можуть запускати аналіз наміру одразу, але будь-яка дія, що створює, змінює або видаляє дані, спочатку формує чернетку та прев'ю. Запис відбувається лише після callback «Підтвердити»; читання списку або розкладу підтвердження не потребує.

### Спільний механізм дій

1. Винести опис, перевірку аргументів і виконання mutating/read-only дій у один спільний модуль. OpenAI, OpenRouter і Google мають лише перетворювати спільний опис інструмента у формат свого SDK та передавати виклик спільному виконавцю.
2. Прибрати прямі звернення AI-провайдерів до `scheduler_service` та БД. Це одночасно усуває вже наявну розбіжність OpenRouter: неправильний порядок аргументів `add_reminder(...)` і виклик неіснуючого `delete_reminder(...)`.
3. Додати серверну валідацію обов'язкових полів, дозволених типів дій, власника чернетки, chat/user scope, часової зони та часу в майбутньому. Вказівки в system prompt залишаються підказкою моделі, але не межею безпеки.
4. Увести персистентну `ActionDraft`: `user_id`, `chat_id`, `source_message_id`, `action_type`, JSON payload, JSON missing fields, status, expiry, timestamps. На пару user/chat допускається одна активна чернетка; нова явно замінює або скасовує стару.
5. Підтвердження, скасування й повторне натискання мають бути ідемпотентними. Callback перевіряє власника; чужий користувач у групі не може підтвердити, перенести чи відмітити чужу дію.

### Уточнення неповної інструкції

1. Якщо бракує часу, часової зони, назви, дозування або опорної події на кшталт сніданку, створити чернетку зі статусом `awaiting_info` і поставити одне конкретне питання за раз.
2. Наступна текстова відповідь користувача спочатку маршрутизується до активної чернетки, а не в загальний чат. Після заповнення всіх полів бот показує повне прев'ю в локальному часі з кнопками «Підтвердити» / «Скасувати».
3. Відносні правила («через дві години після сніданку») не зберігати як нечіткий текст. Після отримання часу сніданку вони перетворюються на конкретні локальні часи; в прев'ю показуються і вихідне правило, і розрахований час.
4. Чернетки мають строк дії. Прострочена чернетка не виконується і пропонує почати налаштування заново.

### Розклад ліків та інших повторюваних завдань

1. Поточну таблицю `Reminder` залишити для одноразових нагадувань. Для повторюваних задач додати нові таблиці, щоб `create_all` міг розгорнути їх без небезпечної зміни існуючої SQLite-схеми:
   - `ScheduledTask`: власник, чат, тип контексту, назва, деталі/дозування, локальний час, timezone, дні тижня, active;
   - `TaskOccurrence`: конкретне спрацювання, planned/due time, status (`scheduled`, `delivered`, `done`, `snoozed`, `skipped`, `missed`), Telegram message ID та timestamps.
2. Для щоденних/тижневих повторів використати наявний APScheduler `CronTrigger` з IANA timezone; для snooze — `DateTrigger`. Визначення і події зберігаються в SQLite, а APScheduler jobs відновлюються на старті.
3. Повідомлення про прийом містить назву, дозування рівно з інструкції користувача та локальний час, а також кнопки «✅ Прийняв», «⏰ +15 хв», «⏰ +30 хв», «⏭ Пропустив».
4. Snooze має бути персистентним і переживати перезапуск. Повторний callback не створює дубліката; для одного task/time використовується унікальна occurrence.
5. Під час старту не засипати чат усіма пропущеними повторюваними подіями: позначити їх `missed` і надіслати максимум одне зведене повідомлення на задачу.
6. Бот не діагностує, не обирає препарат і не вигадує дозу. Він лише структурує надану користувачем/лікарем інструкцію. Якщо доза або правило неоднозначні, підтвердження заблоковане до уточнення.

### Контекстні списки на прикладі покупок

1. Додати `UserList` і `ListItem` як просту модель іменованих списків. Для покупок за замовчуванням використовується список «Покупки».
2. Вибір списку детермінований: явно названа користувачем назва -> поточний список з активної чернетки/діалогу -> єдиний наявний список потрібного типу -> створення списку за замовчуванням. Не використовувати embeddings або окрему векторну БД.
3. Підтримати мінімальний набір дій: показати список, додати один/кілька пунктів, відмітити куплене, повернути пункт, видалити пункт, очистити куплені. Масові зміни виконуються однією транзакцією.
4. У групі список належить чату; автор дії зберігається окремо. У приваті список належить користувачу. Callback завжди перевіряє chat scope.

### Telegram UX та callback-и

1. Використовувати короткі callback-дані, що вкладаються в ліміт Telegram 64 байти: наприклад `draft:ok:123`, `occ:done:456`, `occ:s15:456`, `list:done:789:101`.
2. Редагувати існуюче повідомлення після підтвердження/скасування, щоб кнопка не залишалася активною. Для вже обробленої дії показувати поточний стан без повторного запису.
3. Усі користувацькі поля екранувати перед HTML-виводом. У логах не писати медичні деталі, API-ключі та повний payload; достатньо типу дії та ID.

### Обов'язкова верифікація

1. Unit/contract: усі провайдери віддають однаковий набір дій у спільний executor; невалідний payload не змінює БД; OpenRouter використовує правильну сигнатуру.
2. Voice regression: обробка voice/video-note/video повертає транскрипцію; scheduler та action executor не викликаються; callback бере саме ту транскрипцію, під якою натиснута кнопка.
3. Draft flow: missing breakfast time -> одне уточнення -> прев'ю -> confirm створює записи один раз; cancel/expiry/чужий callback нічого не змінюють.
4. Schedule flow: daily і weekdays, timezone/DST, restore після restart, missed policy, idempotent done, persistent snooze.
5. Shopping flow: reuse існуючого списку, створення default за відсутності, ізоляція чатів/користувачів, atomic multi-item add.
6. Повний існуючий тестовий набір має залишитися зеленим; додати один невеликий файл тестів на кожен новий нетривіальний модуль, без нового test framework або залежностей.

### Свідомо не включено у v2.5.0

1. Медичні рекомендації, взаємодії препаратів, автоматичний вибір дозування та оцінка прихильності — лише нагадування за наданою інструкцією.
2. Універсальний workflow/DSL, embeddings, vector DB, окрема черга повідомлень, web-панель і синхронізація з календарями — додавати лише після окремої потреби.
3. Довільні cron-вирази від моделі — модель передає нормалізовані поля, а застосунок будує дозволений trigger сам.
