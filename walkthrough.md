   - Додано `'timezone': BOT_TIMEZONE` до `DEFAULT_SETTINGS` та `DEFAULT_GROUP_SETTINGS` у `config.py`.
   - У `bot/handlers/common.py` реалізовано безпечний fallback для legacy-записів налаштувань без значення часового поясу (явне збережене `UTC` не перезаписується).
   - Усунено захардкоджений `'Europe/Kiev'` у `timezone_menu` в `bot/handlers/settings.py` на користь `BOT_TIMEZONE`.
   - Реалізовано єдиний хелпер `get_effective_timezone(user_id, chat_id)` у `bot/handlers/common.py`: для груп (`chat_id < 0`) часовий пояс береться виключно з налаштувань групи, що гарантує передачу коректного локального часу в `process_gpt_request` (AI clock prompt та shared tools), `text.py` (уточнення та рендер активних нагадувань) та `callbacks.py` (confirmation `execute_tool`, clarification reply та видалення нагадувань). Налаштування часового поясу автора повідомлення не перекривають груповий контекст.

## Надійність: обробка stale Telegram callback у списку покупок (v2.5.2 patch)

1. **Проблема**:
   При спробі відповісти на прострочений або недійсний callback (`query.answer(...)`) Telegram API повертає виняток `telegram.error.BadRequest: Query is too old and response timeout expired or query id is invalid`.
   У гілці обробки callback-ів списку покупок (`bot/handlers/callbacks.py`) цей виняток перехоплювався загальним блоком `except Exception`, через що помилка некоректно класифікувалася як помилка бази даних (`DB error in list callback`), і викликався повторний `query.answer(...)`, що призводило до другого падіння та зайвого traceback у системному лозі.

2. **Виправлення**:
   - Імпортовано `BadRequest` із `telegram.error` у `bot/handlers/callbacks.py`.
   - У блоці `list:` callback оброблено `BadRequest` окремо перед `except Exception`:
     - Не класифікується як DB-помилка.
     - Повторний виклик `query.answer` не здійснюється.
     - Handler безпечно повертає керування (`return`).
     - Логується коротке попередження виключно з безпечними числовими ідентифікаторами (`action`, `list_id`, `chat_id`, `user_id`) без об'єкта винятку, traceback, тексту пунктів чи назви списку.
   - У fallback-блоці справжньої DB-помилки виклик `query.answer(...)` обгорнуто в `try ... except BadRequest: pass`, щоб прострочений запит під час збою БД не створював traceback.
   - Валідацію вхідних даних списку покупок також захищено від падіння при stale callback.

3. **Верифікація**:
   - Додано регресійний тест `test_55_stale_callback_bad_request_handled_safely` у `test_list_callbacks.py`.
   - Перевірено:
     - `query.answer()` кидає `BadRequest`.
     - Handler не викидає виняток назовні.
     - Callback не викликається вдруге (`call_count == 1`).
     - DB helper не викликається повторно (`call_count == 1`).
     - Логи не містять назви списку, тексту товару, traceback чи рядка винятку, і містять safe IDs.
   - Усі тести списків та чернеток: `.\venv\Scripts\python.exe -m unittest -v test_list_callbacks.py test_draft_callbacks.py` -> **75 passed**, `OK`.
   - Повний набір тестів: `pytest -n auto` -> **453 passed** за 25.32 с.

## Історія: Версія 2.5.0

## Голосові повідомлення

1. Голосові повідомлення, відеонотатки та відеофайли спочатку лише транскрибуються й показуються користувачу.
2. Форматування транскрипції, підсумовування та переформулювання виконуються з вимкненими AI tools і веб-пошуком.
3. Кнопки «Обробити як інструкцію», «Підсумувати» та «Переформулювати» прив'язані до точного ID збереженої транскрипції.
4. Callback перевіряє ID користувача, чату та роль запису. Чужа, видалена або некоректна транскрипція не передається моделі.

## Спільні AI-дії та ActionDraft

1. Схеми, серверна валідація та виконання інструментів зосереджені в `bot/ai/tools.py`; AI-провайдери відповідають лише за свій транспортний формат.
2. Read-only дії можуть виконуватися одразу. Дії, що змінюють дані, спочатку створюють персистентну `ActionDraft` без side effect.
3. Якщо інформації бракує, бот ставить одне уточнення. Наступна текстова відповідь або явно вибрана транскрипція доповнює активну чернетку.
4. Повна чернетка показує прев'ю та виконується тільки після callback підтвердження. Ownership, expiry, cancel і повторні натискання перевіряються атомарно.

## Повторювані розклади

1. `ScheduledTask` зберігає правило медикаментозної або загальної задачі, а `TaskOccurrence` — конкретне спрацювання та його стан.
2. Підтримуються щоденні й weekday-розклади в IANA timezone, включно з DST gap/fold. Бот структурує лише введені користувачем назву, дозування та час і не вигадує медичних рекомендацій.
3. Сповіщення мають кнопки «Прийняв/Виконав», `+15 хв`, `+30 хв` і «Пропустив». Переходи станів і snooze персистентні та ідемпотентні.
4. Після перезапуску APScheduler відновлює майбутні задачі й snooze з SQLite. Прострочені occurrence атомарно стають `missed`, а чат отримує не більше одного зведення на задачу.

## Списки покупок

1. `UserList` і `ListItem` реалізують іменовані списки; за відсутності відповідного списку використовується «Покупки».
2. Бот уміє показувати список, атомарно додавати кілька пунктів, позначати куплене, повертати пункт до активних, видаляти пункт і очищати куплені.
3. Зміни через AI проходять через `ActionDraft`, а показ списку залишається read-only.
4. Telegram inline-кнопки оновлюють повідомлення з фактичного стану БД. Усі lookup і mutation helpers перевіряють `chat_id`; чужі та неіснуючі ID не розкривають наявність даних в іншому чаті.
